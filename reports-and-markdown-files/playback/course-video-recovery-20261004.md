## External API contract and boundaries

Only the independently deployed DRM API was modified; no worker, processing, media, DRM provider or database schema change. Platform code continues to consume external HTTP APIs and never queries external persistence.

- `GET /v1/admin/users/:externalUserId/devices`: application authentication; tenant comes solely from credentials. Safe registration references, status/timestamps, active-unexpired-session flag and releasability; maximum device count and a truncation flag. No raw browser ID, IP, token or secret. List is bounded to 100 entries; recovery refuses a truncated inspection.
- `POST /v1/admin/users/:externalUserId/devices/:deviceReference/release`, empty JSON body: UUID reference, bounded user identifier, tenant/user-scoped lookup. Idempotent missing/repeated release; refuses ACTIVE unexpired playback and all REVOKED registrations with safe 409 codes.
- Release takes the same per-user advisory lock as session registration, locks the row, deletes only an inactive ACTIVE registration and commits its audit in the same transaction. Audit failure rolls back release. Existing session/audit history remains. A released legitimate browser can re-register normally within the existing limit; a banned browser remains banned.

Implementation: external `apps/api/src/services/device-recovery.service.ts`, `modules/admin/routes.ts`, a focused integration suite/config and disposable Docker Compose harness. No new user role or backend application. Existing application credentials remain server-side.

## Improvements found — recommendations for a separate assignment

1. **ADMIN device recovery UI:** show slot counts, last seen and active/inactive state, with an audited release action and a clear refusal when playback is active. The new external API supports this; platform routing, ADMIN permission/CSRF controls and UI are additional work. Do not expose application credentials or silently auto-release student devices.
2. **Abandoned-session recovery:** abruptly closing the verification browser demonstrated that best-effort navigation closure can leave a stream slot occupied. Evaluate a shorter heartbeat-backed activity lease or a clearly scoped own-session recovery flow. This changes external session policy and needs its own owner assignment; do not terminate other sessions automatically or relax stream limits.
3. **First-use cross-tab identity race:** the platform fix prevents normal new-tab identity churn, but two tabs simultaneously generating their first ID can still race between storage read and write. Add browser-level coordination and a concurrent-first-tab regression before calling that edge case solved. Browser storage cleared/blocked remains an explicit separate installation/fallback scenario, not a bypass.
4. **Playback controls and failure feedback:** handle the rejected `video.play()` promise and show an accessible actionable message; include play/pause in the fullscreen frame as a consistent custom control, while retaining native controls and watermark. The current custom play button sits outside that frame. Never retry denials in a way that consumes more device/session quota.
5. **Longer real-media verification:** add a fixture long enough to cover renewal, saved-position resume after reload, expiry refusal, Arabic/English captions and mobile fullscreen. Verify a real uploaded recording alongside the short test pattern. Keep search, accurate duration labels, bilingual captions and protected resources in [the two-agent feature plan](../course-learning/course-learning-enhancements-plan.md), with its existing ownership contract.
6. **Bounded health checks:** the external `/health` handler awaits database, cache and object-storage checks without explicit per-check timeouts. Add bounded dependency checks so a slow storage request returns a useful degraded state promptly. This is additional external maintenance, not implemented under the device-recovery assignment.

The storage diagnosis is consistent with the primary browser documentation: [MDN sessionStorage](https://developer.mozilla.org/en-US/docs/Web/API/Window/sessionStorage) describes tab-specific page sessions, while [MDN Web Storage](https://developer.mozilla.org/en-US/docs/Web/API/Web_Storage_API) describes shared same-origin local storage. Only the non-credential installation identity belongs there; authentication and playback tokens remain cookies/transient memory. Browser media compatibility still needs explicit [EME capability verification](https://developer.mozilla.org/en-US/docs/Web/API/Encrypted_Media_Extensions_API); this local ClearKey proof does not establish commercial Widevine/FairPlay provisioning.
