# FAYQ website UX review — 2026-10-02

Implementation follow-up: the owner subsequently requested all UX packages and optional features after clarification. See [the implementation checklist and verification](../ux-improvements-20261002/report.md). The original findings and screenshots below remain the historical audit, rather than a current outstanding-work list.

The platform has its main public, student and admin pages. The largest UX gap is the admin authoring experience: many independent tasks share one long course page, and errors do not reliably explain what to correct. Improve that workflow before adding more business features.

This is a browser walkthrough and source review, supported by published UX guidance. It does not prove the best design through user testing. Recommendations below are proposals for owner selection, not additional accepted scope.

## Small proposed delivery packages

1. **Admin errors and unsaved drafts:** action-specific popup/field feedback, obsolete-error cleanup, save status and navigation protection. Verify incomplete save, repeated save, cancelled editing, failed requests and keyboard navigation without losing values.
2. **Course management clarity:** course tabs/sections, translated readiness states, one archive action and named entity deletion controls. Preserve API transitions, paid access and deletion safeguards. Verify two populated courses with multiple sections/lessons in Arabic/English and mobile.
3. **Assessment workspace:** dedicated editor and visible Save/Prepare/Review/Publish progress. Verify exact-draft readiness, published-version preservation, private-code exclusion, required/optional choice and legacy assessment compatibility.
4. **Admin lists and review:** catalog filtering, package eligibility guidance, submission/recharge review layout, summary task links. Any new server list/filter API should be bounded and reviewed separately. No bulk financial approvals or destructive bulk actions.
5. **Student journey polish:** course identity in purchases, login/signup links, owned-course continuation, Arabic copy corrections, recharge unavailable state and locked-lesson assessment links.

Each package should retain FAYQ theme tokens, mandatory translations, cookie sessions, exactly two roles and the existing one-backend architecture. Use Docker and synthetic fixtures, verify changed behavior, and clean only the package's inspected resources. Do not dispatch OpenCode, commit or push from this review. No OpenCode executable was found on PATH during this audit.

Possible new pages/features needing an owner decision: a student directory beyond allowance lookup; support/help/contact; owner-approved terms/privacy/refund content; profile editing/password changes; password recovery and identifier verification with an approved delivery channel. These are not inferred missing requirements. An unknown hash currently falls back to Home; a clear not-found screen is an additional navigation improvement proposal.

The sample ICT curriculum also contains Python and HTML/CSS. Current in-platform execution remains JavaScript-only. Adding other execution languages, visible DOM previews or automatic content conversion requires separate scope. Production deployment, commercial DRM, monitoring/recovery activation and 10,000-user qualification remain deferred.

## Research supporting the recommendations

- Reducing initially visible secondary controls and grouping advanced work can reduce learning burden. That supports the proposed focused admin workspaces; the exact grouping remains an inference to validate with actual admins. [Nielsen Norman Group: Progressive Disclosure](https://www.nngroup.com/articles/progressive-disclosure/).
- Error feedback should explain how to correct a mistake and associate the message with its field. Keep the requested popup and add precise field feedback; do not return to top-of-page-only errors. [W3C WAI: User Notification](https://www.w3.org/WAI/tutorials/forms/notifications/), [GOV.UK: Error message](https://design-system.service.gov.uk/components/error-message/).
- Search, sorting and pagination are established options for managing larger record lists. Apply only what each FAYQ list needs; the existing submission pagination should be retained. [IBM Carbon: Data table guidelines](https://www.carbondesignsystem.com/building-blocks/core/components/data-table/guidelines).
- A review step lets users inspect entered information before a consequential submission. This supports an explicit publishing review with bilingual completeness, samples and preparation status. [GOV.UK: Check answers](https://design-system.service.gov.uk/patterns/check-answers/).

Next design validation should use real representative admins completing three tasks: add/publish a bilingual problem, find/review a student submission, and verify a recharge. Record completion, errors and needed help. No time targets or acceptance thresholds are imposed by this review.
