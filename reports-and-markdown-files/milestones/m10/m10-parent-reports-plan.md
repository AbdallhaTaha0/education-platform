# M10: Parent reports and course student tracking

Date: 2026-10-07, Africa/Cairo. Status: planning only; owner answers below confirm product direction, not implementation authority. Unanswered choices remain open.

## Confirmed owner direction

- Generate reports on demand only: ADMIN selects a report type and presses the report/send action. The platform prepares the text and opens the registered guardian's WhatsApp chat. ADMIN sends inside WhatsApp. This supersedes the earlier automatic scheduling/due-queue proposal; no scheduled background dispatch or downtime catch-up is needed.
- Each course offers three composable report types: week (7 days), two weeks (14 days = Week 1 + Week 2), and month (four weeks/28 days = four weekly sections). Month here is not a calendar month. The owner approved rolling windows ending when ADMIN clicks to generate, split into consecutive weekly sections with exact Cairo dates.
- Support both combined student reports and reports for one course.
- Detailed per-video view counts are for ADMIN tracking. Parent reports show whether the student viewed each video, and quiz/assignment results; numeric view counts are not part of the parent template unless later requested.
- Latest owner correction supersedes the earlier refresh/reconnect exclusion: refreshing or successfully reconnecting playback starts another countable viewing session. Each session counts once after at least 30 seconds of actual playback; continuous watching does not count again every 30 seconds. Returning for a new session also counts after its threshold. Failed reconnect attempts and duplicate telemetry deliveries are not successful playback sessions. Plain pause/resume and token renewal without a playback restart do not count again. A counted view does not mean the video was completed. Engineering design must distinguish successful session restarts from low-level retries and preserve the accepted threshold.
- ADMIN sends to the guardian number already registered. No additional contact-verification service, parent account or confirmation gate is assigned. Existing contact editing permissions remain; a changed number must refresh the send preview/action.
- Include zero-activity students so parents can follow up.
- Course reporting follows the student's course membership/access through the course's end/removal. October and November are separate course contexts: new-course activity does not overwrite or reset old-course evidence. The owner described access lasting until ADMIN removal or the course ends; M10 must use existing approved course/access terms, not rewrite subscriptions, infer new deadlines or extend expired grants. If actual offer settings conflict with this intended lifecycle, identify that separately before implementation.
- Cover the registered population without an invented business cap. Course rosters still contain actual enrolled students; registration alone does not grant course access.
- No paid WhatsApp API. Formatted text is approved; maximize preparation automation.
- The owner approved disposal at WhatsApp handoff: discard the platform's temporary report text immediately after handing it to WhatsApp. If needed again, ADMIN generates a new report with the button. Do not persist report snapshots, report archives or sending-history records. Underlying viewing/assessment records remain available for regeneration under their applicable lifecycle. Disposal applies to platform-held report copies, not the WhatsApp draft/message. The platform cannot observe Send through click-to-chat and must not claim delivery or sending confirmation.

Latest clarification supersedes the earlier due-course grouping: there are no scheduled due reports. ADMIN chooses the course or a combined report over selected current course memberships; the exact combined-course selection UI is an engineering proposal. Keep each course's dates explicit and preserve underlying historical learning evidence, not generated report archives. Retired-course historical browsing is distinct from current-course report generation.

## Approved text format and proposed layout

Use a concise Arabic WhatsApp text report with FAYQ branding, clear dates, short course sections and one lesson per line. This gives the exact requested ready-to-send workflow without an attachment or parent login. Provide an English counterpart consistent with project localization. Long reports require a reviewed fallback such as numbered message parts with copy controls; do not silently truncate or assume unlimited click-to-chat URL length.

Fields: student name, reporting period, course name, viewed/not viewed status per video, quiz/assignment results and an optional ADMIN note. Use clear labels such as viewed (not necessarily completed), not viewed, and tracking unavailable. Assessment results must distinguish passed, not yet passed, not submitted, checking and service error; never label an unsubmitted or infrastructure-failed assessment as a wrong answer. Partial-period tracking must not be presented as reliable zero activity.

Proposed parent layout: FAYQ heading, student and exact dates, short summary, one course section, video-status lines, quiz/assignment lines and optional follow-up. Two-week reports retain Week 1 and Week 2 sections; four-week reports retain four weekly sections, each with an accurate combined summary. All report types use the same canonical weekly aggregation over recorded events, without requiring earlier reports to have been generated or sent. Video "viewed" in any constituent week means viewed in the combined period; lesson counts must not be summed as though repeat views were different lessons. Show assessment attempts in the correct week and earned-pass status separately; repeated attempts/passes must not fabricate extra completed assessments. Numeric scores/percentages appear only if already supported by the relevant assessment, not invented from view counts or submission counts.

A designed PDF/image can be an optional download later if requested, but a click-to-chat URL pre-fills text and does not attach a generated document. Attachment sharing needs a separate admin action or a supported device share flow; neither is guaranteed by click-to-chat. No paid messaging/report service is needed for text preparation; existing hosting/storage costs remain.

Official source checked 2026-10-07: [WhatsApp click-to-chat documentation](https://faq.whatsapp.com/5913398998672934). It documents a recipient number and URL-encoded pre-filled message. [Official platform pricing](https://business.whatsapp.com/products/platform-pricing) distinguishes chargeable messages and free response scenarios. Unattended sending is outside this plan.

## Tracking and operational boundaries

Current LessonProgress stores resume position, completion and last access; it is not a view ledger. New view counts begin when M10 tracking starts. Older activity is shown as not recorded, not zero, for periods before coverage. Client playback evidence can establish reported playback activity but cannot prove human attention or eliminate fabricated clients.

Use client/ and server/, the existing modular Express backend, platform PostgreSQL/Prisma and existing approved background mechanisms. No new business API service, parent role, DRM source/database access, playback security changes or entitlement changes. Viewing telemetry should use bounded batches/indexed aggregates, not one request per frame. Paginate rosters, prepare reports in batches and resume interrupted jobs. These are engineering proposals, not certification of 10,000-user throughput.

Reports contain no national IDs, wallet details, private assessment answers, credentials or protected media links. Platform report access is ADMIN-only; the prepared message is intentionally shared with the registered guardian. Report responses need no-store cache policy and report bodies/recipient-bearing click-to-chat URLs must not be logged. No extra contact-confirmation requirement is inferred. Changing guardian contact must not leave a ready action silently pointing at the old number. Destroying the platform's temporary report does not remove the WhatsApp draft/message from the sender's or parent's device; no such remote deletion is promised.

Generation runs when ADMIN clicks, so no scheduled service or always-on laptop is required for scheduled reports. The platform still needs to be running and reachable to record playback or generate a report. The platform opens the currently logged-in WhatsApp sender's account; it does not provision or authenticate a WhatsApp business number.

All implementation/review prompts must explicitly require owned Docker cleanup on success, failure or stop: inspect project labels, resolved names and every mount first; remove only owned disposable containers, networks, volumes and fixtures; preserve retained data/previews, reusable images and evidence; no global prune. Record cleanup evidence. No test environment was created for this planning document.
