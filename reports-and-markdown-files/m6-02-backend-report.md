## Storage and API behavior

NotificationEvent retains generic type/version and an opaque optional course reference; Notification resolves those through its retained audience/event rather than copying them. InboxState stores lastSequence and revision; allocation uses lastSequence+1. The source's recordedAt is logical notice creation, so delayed materialization does not restart the approved 180-day period. Exact cutoff is enforced on all APIs even while rows await later physical cleanup. Event and notice retention arithmetic is also enforced by SQL checks.

Internal materialization rechecks duplicate event/recipient after the inbox lock, does not consume another sequence on retry, and refuses a missing audience or expired source. Its transaction rolls back notice, counter and audience changes together on failure. It does not emit a signal or provide a source producer.

| Public route | Behavior |
| --- | --- |
| GET `/api/notifications` | Own nonexpired items ordered by descending recipient sequence; limit 1–50/default 20; optional unreadOnly and sequence cursor; coherent items/count/revision/fence snapshot |
| GET `/api/notifications/unread-count` | Own count/revision/throughSequence; no query fields |
| PUT `/api/notifications/:id/read-state` | Exact boolean read field; own nonexpired row only; identical retries are no-ops |
| POST `/api/notifications/read-all` | Exact decimal-string throughSequence; reject fences beyond the own inbox; later arrivals remain unread |

Both STUDENT and ADMIN may inspect only their own inbox. Current planned producers target STUDENT only. Foreign, missing and expired notification IDs share the same 404 code/message; each response retains the standard requestId. BigInts are decimal strings, not unsafe JSON numbers. Reads use repeatable-read transactions; writes serialize with materialization on InboxState. All responses use no-store. Redis or database availability failures in the notification path return a sanitized 503 and do not bypass durable session checks.
